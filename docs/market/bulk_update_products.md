# Склад — Массовое изменение бренда / категории / поставщика у товаров

**Страница:** `/crm/sklad` (фронт: `src/Components/Sectors/Market/Warehouse/`).
Та же операция продублирована на складе барбера/стройки (`src/Components/Deposits/Sklad/`).
**Эндпоинт:** `PATCH /main/products/bulk-update/`
**Статус:** ⛔ Эндпоинта нет — требуется реализация на бэкенде.
**Связанный существующий эндпоинт:** `DELETE /main/products/bulk-delete/` (массовое удаление) — новый эндпоинт делаем по той же схеме.

---

## 1. Задача

На странице склада у каждого товара в таблице есть чекбокс. Пользователь отмечает
несколько товаров (или все на странице) и одной операцией меняет у них:

- **бренд** (`brand`),
- **категорию** (`category`),
- **поставщика** (`client`).

Меняются **только те поля, которые пользователь явно отметил** в модалке. Остальные
поля товара (цена, количество, штрихкод, PLU и т.д.) не должны затрагиваться.

Типовой сценарий: завезли 300 позиций одного поставщика, у всех проставлена не та
категория — сейчас приходится открывать каждый товар по отдельности.

## 3. Контракт

### 3.1 Запрос

```http
PATCH /main/products/bulk-update/
Authorization: Bearer <access_token>
Content-Type: application/json
```

```json
{
  "ids": [
    "0f5d0c9a-1f0b-4a5e-9c11-2b3d4e5f6a7b",
    "1a2b3c4d-5e6f-4711-8899-aabbccddeeff"
  ],
  "brand_name": "Coca-Cola",
  "category_name": "Напитки",
  "client": "9c8b7a65-4321-4def-9876-0123456789ab",
  "require_all": false
}
```

### 3.2 Поля тела запроса

| Поле | Тип | Обяз. | Описание |
|---|---|---|---|
| `ids` | array[uuid] | да | ID товаров. Минимум 1, максимум 1000 за запрос. Дубликаты схлопываются. |
| `brand_name` | string \| null | нет | Новый бренд **по имени**. `null` — очистить поле. |
| `category_name` | string \| null | нет | Новая категория **по имени**. `null` — очистить поле. |
| `client` | uuid \| null | нет | Новый поставщик (`main/clients/` с `type = "suppliers"`). `null` — очистить. |
| `require_all` | bool | нет | По умолчанию `false`. См. п. 3.3. |

Имена полей `brand_name` / `category_name` выбраны намеренно — ровно их принимают
существующие `POST /main/products/create-manual/` и `PATCH /main/products/{id}/`,
которыми пользуются формы создания и редактирования товара. Дополнительно бэкенд
**должен** принимать алиасы `brand` и `category` (строка = имя, UUID = id) — их шлёт
модалка редактирования товара в `Deposits/Sklad/EditModal`.

**Ключевые правила:**

1. Отсутствие ключа в теле и `null` — **разные вещи**. Ключа нет → поле не трогаем.
   `null` → поле очищаем. Реализуется через проверку по `serializer.initial_data`
   (в DRF — `if 'brand_name' in self.initial_data`), не по `validated_data`.
2. Должно быть передано **минимум одно** из полей `brand_name` / `category_name` /
   `client`, иначе `400` с `detail: "Не передано ни одного поля для изменения"`.
3. Любые другие поля товара в теле (`price`, `quantity`, `barcode`, …) **игнорируются**
   — эндпоинт умеет менять только справочные привязки. Если пришло что-то ещё —
   молча отбросить (не `400`), чтобы не ломать фронт при будущих доработках.
4. Метод — `PATCH`. `POST` на тот же URL можно поддержать как алиас.

### 3.3 Семантика `require_all`

| Значение | Поведение |
|---|---|
| `false` (по умолчанию) | Обновляем все доступные товары из `ids`. Недоступные/несуществующие складываем в `skipped` и возвращаем `200`. |
| `true` | Если хотя бы один ID недоступен или не найден — не обновляем **ничего**, возвращаем `400` со списком проблемных ID. |

### 3.4 Ответ `200 OK`

```json
{
  "updated": 12,
  "failed": 0,
  "requested": 14,
  "updated_ids": ["0f5d0c9a-…", "1a2b3c4d-…"],
  "skipped": [
    { "id": "aaaaaaaa-…", "reason": "not_found" },
    { "id": "bbbbbbbb-…", "reason": "forbidden" }
  ],
  "applied": {
    "brand": { "id": "…", "name": "Coca-Cola" },
    "category": { "id": "…", "name": "Напитки" },
    "client": { "id": "…", "full_name": "ОсОО Ромашка" }
  }
}
```

| Поле | Описание |
|---|---|
| `updated` | Сколько товаров реально обновлено |
| `failed` | Сколько не обновлено (= длина `skipped`) |
| `requested` | Сколько уникальных ID пришло |
| `updated_ids` | ID успешно обновлённых |
| `skipped` | Массив `{ id, reason }`, `reason` ∈ `not_found` \| `forbidden` \| `other_branch` \| `deleted` |
| `applied` | Что именно было применено (для сверки на фронте) |

Фронт читает `updated` и `failed`; при `failed > 0` показывает
«Обновлено товаров: N, не удалось: M». Остальные поля — для отладки и на будущее.

### 3.5 Ошибки

| Код | Когда | Тело |
|---|---|---|
| `400` | Пустой `ids`, невалидный UUID, не передано ни одного изменяемого поля, `require_all=true` и есть проблемные ID | `{ "detail": "…", "ids": ["…"] }` |
| `400` | Бренд/категория/поставщик не найдены (см. п. 4) | `{ "detail": "Бренд «Coca-Cola» не найден" }` |
| `401` | Нет/протух токен | стандартный DRF |
| `403` | Роль без права редактировать товары | `{ "detail": "Недостаточно прав" }` |
| `413`/`400` | `len(ids) > 1000` | `{ "detail": "За один запрос можно изменить не более 1000 товаров" }` |

Текст в `detail` — на русском, он показывается пользователю как есть.

## 4. Разрешение бренда / категории / поставщика

Бренд и категорию фронт шлёт **по имени** (в справочниках на фронте есть и `id`,
но текущие ручки создания/редактирования товара работают по имени). Правило
разрешения:

1. Значение парсится как UUID → ищем по `id` **в пределах компании**.
2. Иначе — ищем по `name` (регистронезависимо, с `strip()`) в пределах компании.
3. Не нашли → `400` с понятным текстом. **Создавать новый бренд/категорию
   на лету в этом эндпоинте нельзя** — создание идёт через `POST /main/brands/`
   и `POST /main/categories/`, фронт делает это отдельно.

Для `client`: только UUID, должен принадлежать компании и иметь `type = "suppliers"`.
Иначе — `400` `{ "detail": "Поставщик не найден" }`.

---

## 5. Права и изоляция данных

1. **Компания.** Обновляются только товары `company = request.user.company`. Товар
   чужой компании → `skipped` с `reason: "forbidden"` (при `require_all=false`),
   даже если ID существует. Наружу не должно утекать различие «не существует» /
   «чужой» — но внутри логов это различие фиксировать полезно.
2. **Филиал.** Если у пользователя ограничение по филиалу (не owner/admin),
   обновлять можно только товары своего филиала; остальные → `reason: "other_branch"`.
3. **Роли.** Право то же, что у `PATCH /main/products/{id}/`. Кассир без права
   редактирования товаров получает `403` на весь запрос.
4. Удалённые (soft-deleted) товары не обновляются → `reason: "deleted"`.

---

## 6. Реализация: требования

1. **Атомарность.** Всё в одной транзакции (`transaction.atomic`). При
   `require_all=true` любая проблема → полный откат.
2. **Один UPDATE, а не N.** Ожидается `Product.objects.filter(id__in=allowed_ids).update(**changes)`,
   а не цикл с `save()`. Иначе смысл эндпоинта теряется — на 1000 товаров фронт
   и сейчас может сделать 1000 PATCH'ей.
   Если на модели висят сигналы/пересчёты, которые обязаны отработать, — сделать
   `bulk_update` с явным списком полей, но всё равно одним запросом к БД.
3. **Не трогать `updated_at`-зависимую логику продаж.** Изменение бренда/категории
   не должно порождать движений по складу, кассе или истории приходов.
4. **История/аудит.** Если в проекте есть журнал изменений товара — записать одну
   запись на операцию (пользователь, время, список ID, какие поля на что изменены),
   а не по записи на товар.
5. **Кэш.** Инвалидировать кэш списка товаров и любых агрегатов по
   брендам/категориям/поставщикам (аналитика группируется по этим полям).

## 7. Проверочные сценарии (для приёмки)

| # | Сценарий | Ожидаемый результат |
|---|---|---|
| 1 | 3 валидных ID, только `category_name` | `updated: 3`, категория изменена, бренд и поставщик у товаров прежние |
| 2 | Тело без `brand_name`/`category_name`/`client` | `400`, ничего не изменено |
| 3 | `brand_name: null` | Бренд очищен (`null`), остальное не тронуто |
| 4 | 2 своих ID + 1 чужой компании, `require_all=false` | `200`, `updated: 2`, `failed: 1`, `reason: "forbidden"`; чужой товар не изменён |
| 5 | То же с `require_all=true` | `400`, **ни один** товар не изменён |
| 6 | Несуществующий бренд по имени | `400`, ничего не изменено, новый бренд **не создан** |
| 7 | `client` с `type != "suppliers"` | `400` |
| 8 | 1000 ID | `200`, отрабатывает без таймаута (ориентир — до 2 сек) |
| 9 | 1001 ID | `400` с сообщением о лимите |
| 10 | Пользователь без прав на редактирование товаров | `403`, ничего не изменено |
| 11 | Повторный запрос с тем же телом | Идемпотентно: `updated` то же число, побочных эффектов нет |
| 12 | После изменения категории у 50 товаров | Аналитика по категориям пересчитана с новыми значениями |

## 8. Что фронт делает после успешного ответа

1. Закрывает модалку, снимает выделение со всех товаров.
2. Показывает алерт: «Выбранные товары обновлены» либо, если `failed > 0`,
   «Обновлено товаров: N, не удалось: M».
3. Перезапрашивает `GET /main/products/list/` с текущими страницей, поиском и
   фильтрами — то есть ответ на bulk-update **не обязан** содержать сами товары.
