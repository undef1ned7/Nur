## 2. Общее: права на опасные операции

Пункты B02, B03, B07, B06 и B15 упираются в одно: **у сервера нет прав на опасные операции**,
он выполняет всё, что прислал клиент. QA шёл под владельцем, поэтому как ведут себя другие роли,
не проверялось. Судя по поведению API, проверок прав в этих местах нет совсем.

Предлагаемые права (на уровне сотрудника, по образцу существующих `can_view_*`):

| Право | Что разрешает | По умолчанию |
|---|---|---|
| `can_post_negative_stock` | проводить документ с `allow_negative=true` | только owner |
| `can_unpost_documents` | отменять проведение документов | owner, admin |
| `can_change_document_date` | ставить дату документа не сегодняшнюю | owner, admin |
| `can_post_closed_period` | проводить или отменять документы в закрытом периоде | только owner |
| `can_cash_negative` | проводить расход, который уводит кассу в минус | только owner |

Правила для всех пунктов ниже:

- проверка **только на сервере**, в сервисе проведения (`post_document`, `unpost_document`,
  проведение денежных документов), а не во view: тот же сервис вызывают мобильное приложение,
  корзины агентов и т.д.;
- ответ при отказе — `403` с `code`, по которому фронт покажет понятный текст:

```json
{ "detail": "Недостаточно прав: проведение в минус", "code": "permission_negative_stock" }
```

- ответ при нарушении бизнес-правила — `400` с `code` (коды — в каждом пункте).

Фронт покажет `detail` как есть, а по `code` может предложить действие.

### B01 + B31. Перемещение портит остатки чужих товаров

**Эндпоинты:** `POST /api/warehouse/documents/transfer/`, `POST /api/warehouse/documents/{id}/post/`.

**Как воспроизвести:**

1. Склад A: товар «QA Товар 1», код `0001`, остаток 5.
2. Склад «тест»: свой товар «товар склада тест (мясо», тоже код `0001`.
3. Перемещение 2 шт «QA Товар 1» со склада A на склад «тест», провести.

**Ожидаемо:** на складе «тест» появляется (или пополняется) «QA Товар 1» +2.
**Фактически:** +2 зачислено на «товар склада тест (мясо», потому что у него тот же код `0001`.

**Причина:**

- товар — это копия (`WarehouseProduct`) в каждом складе, общего справочника товаров компании нет;
- код товара генерируется **в рамках склада** и в каждом складе начинается с `0001` (B31);
- при проведении перемещения товар на складе-получателе ищется в том числе по коду
  (`_get_or_create_transfer_product` в `services.py`).

> ⚠️ В [backend-remaining-2026-10.md](./backend-remaining-2026-10.md) R11 предложена цепочка
> «штрихкод → **код** → артикул+название → новая карточка». Шаг «код» в ней **неверный**, пока коды
> не уникальны в рамках компании. Именно он и вызывает B01.

**Последствия:** остатки всех складов, где были перемещения, недостоверны. Аналитика по складам
и стоимость склада (`warehouse_on_hand_amount`) тоже.

**Сделать (этап 1, срочно — закрывает ошибку):**

1. Связь между копиями товара: поле `WarehouseProduct.source_product` (FK на себя, nullable) или
   общий ключ `product_group_id` (UUID), одинаковый у всех копий одного товара в компании.
2. При проведении перемещения искать товар-получатель **строго** в таком порядке:
   1. та же группа (`product_group_id`) на складе-получателе;
   2. тот же **штрихкод** (непустой) на складе-получателе;
   3. иначе — **создать новую карточку** на складе-получателе (копия: название, единица, цены,
      штрихкод, категория, бренд) с тем же `product_group_id`.

   Сопоставление по коду и по названию **убрать полностью**.
3. Если по штрихкоду нашлось несколько товаров — `400`:

```json
{
  "detail": "На складе «тест» несколько товаров со штрихкодом 4870…: «…», «…». Уточните товар.",
  "code": "transfer_target_ambiguous"
}
```

4. Ответ проведения: в каждой строке вернуть `target_product` (id + название), чтобы фронт показал,
   куда зачислено.

**Сделать (этап 2 — B31, архитектура):**

- код товара уникален **в рамках компании** (сквозная нумерация по компании, `unique_together =
  (company, code)`), а не склада;
- целевое решение — единый справочник товаров компании и остатки по складам (`StockBalance`
  уже хранит пару склад + товар). Это пункт «Единый справочник товаров» из листа «Чего не хватает»,
  его надо проектировать отдельно. Этап 1 нужен, чтобы перестать портить данные уже сейчас.

**Данные (разово):**

- команда `report_transfer_mismatches` (dry-run): для каждого проведённого `TRANSFER` сравнить
  товар-источник и товар-получатель (название, единица, штрихкод). Выдать список пар, где
  совпал только код или только название;
- по отчёту — решение владельцев (D-B01): исправлять ли остатки документами `INVENTORY` или
  перепроводить перемещения;
- проставить `product_group_id` существующим копиям: одинаковый штрихкод в компании → одна группа,
  остальные — каждая своя группа.

**Приёмка:**

- [ ] Сценарий из «Как воспроизвести»: +2 у «QA Товар 1» на складе «тест», у «мяса» остаток не изменился.
- [ ] Перемещение товара без штрихкода на склад, где его нет, создаёт новую карточку.
- [ ] Повторное перемещение того же товара пополняет ранее созданную карточку, а не создаёт вторую.

### B04. Возврат продажи не привязан к продаже

**Эндпоинт:** `POST /api/warehouse/documents/sale-return/` + `post`.

**Как воспроизвести:** клиенту продано всего 5 шт → возврат продажи этому клиенту 20 шт за наличные.
**Фактически:** проведено, из кассы выдано 3 000 сом, остаток вырос на 20. Это готовая схема
вывода денег и товара.

**Модель:**

```python
class Document(models.Model):
    # ...
    base_document = models.ForeignKey(
        "self", null=True, blank=True, on_delete=models.PROTECT,
        related_name="returns",
        help_text="Продажа (для SALE_RETURN) или закуп (для PURCHASE_RETURN), по которой оформлен возврат",
    )

class DocumentItem(models.Model):
    # ...
    base_item = models.ForeignKey(
        "self", null=True, blank=True, on_delete=models.PROTECT,
        related_name="returned_items",
    )
```

**Контракт создания возврата:**

```http
POST /api/warehouse/documents/sale-return/
{
  "base_document": "<uuid продажи>",
  "items": [
    { "base_item": "<uuid строки продажи>", "qty": "2" }
  ],
  "payment_kind": "cash"
}
```

- товар, цена, скидка и контрагент берутся **из строки продажи**, а не из запроса;
- для `PURCHASE_RETURN` — то же самое по закупу.

**Проверки при проведении:**

| Проверка | Ошибка |
|---|---|
| `base_document` не указан | `400 return_base_required` |
| `base_document` не `POSTED` или другого контрагента/компании | `400 return_base_invalid` |
| `qty` > проданное − уже возвращённое по этой строке (учитывать только проведённые возвраты) | `400 return_exceeds_sold` |
| сумма к выдаче из кассы > суммы, фактически оплаченной по продаже | `400 return_exceeds_paid` (остаток — уменьшением долга клиента) |

```json
{
  "detail": "По строке «…» продано 5, уже возвращено 0. Вернуть можно не больше 5.",
  "code": "return_exceeds_sold",
  "items": [{ "base_item": "<uuid>", "sold": "5", "returned": "0", "requested": "20" }]
}
```

Нужен эндпоинт для фронта, чтобы показывать, сколько можно вернуть:

```http
GET /api/warehouse/documents/{id}/returnable/
→ { "items": [{ "base_item": "<uuid>", "product": "<uuid>", "name": "…",
               "sold": "5", "returned": "1", "returnable": "4", "price": "150.00" }] }
```

**Переходный период:** старые возвраты без `base_document` остаются как есть. Новые без
`base_document` — запрещены сразу после выкладки фронта (согласовать дату). До этого — разрешены
только с правом `can_post_negative_stock`.

**Приёмка:**

- [ ] Сценарий выше → `400 return_exceeds_sold`, касса и остаток не изменились.
- [ ] Возврат 2 из 5 проходит; второй возврат 4 из оставшихся 3 → `400`.
- [ ] Отмена проведения возврата возвращает «возвратное» количество (ещё раз можно вернуть).
- [ ] `returnable` отдаёт верные цифры с учётом проведённых возвратов.
- [ ] То же для возврата поставщику.

### B05. Старые наличные продажи числятся долгом клиента (данные)

**Где видно:** карточка контрагента «Кылым»: в блоке «Продажи» — «наличные 15 800, в долг 0»,
а «Общие долги» — «15 800, контрагент должен вам». Общая дебиторка в списке контрагентов —
28,3 млн сом, это значение искажено.

**Причина:** у старых проведённых продаж с `payment_kind=cash` нет денежного документа
(`MONEY_RECEIPT`). Долг считается как «продажи − поступления», поэтому оплаченная продажа
выглядит долгом. **Новые продажи создают денежный документ правильно** — это проверено.

**Сделать:**

1. Команда `fix_sale_money_documents` (по образцу `fix_receipt_money_documents`), по умолчанию dry-run:
   - найти проведённые `SALE` с `payment_kind ∈ {cash, card, transfer}` (или предоплатой > 0),
     у которых нет проведённого `MONEY_RECEIPT` с `source_document = продажа`;
   - отчёт по компаниям: количество, сумма, период, касса;
   - `--apply`: создать и провести `MONEY_RECEIPT` на оплаченную часть, **датой продажи**,
     с системной категорией «Продажа», в кассу склада продажи (по правилам R13).
2. Решение D-B05: влияют ли созданные приходы на остаток кассы. Деньги физически уже пришли и,
   скорее всего, уже учтены где-то вручную. Вариант по умолчанию — создавать приход с флагом
   `is_migration=true`, который **не меняет** остаток кассы, но закрывает долг.
3. После применения — пересчитать кэш аналитики и сальдо контрагентов.

**Приёмка:**

- [ ] Отчёт dry-run передан владельцам, решение D-B05 принято.
- [ ] У «Кылым» после миграции «Общие долги» = 0 (если других долгов нет).
- [ ] Повторный dry-run — 0 продаж без денежных документов.
- [ ] Остатки касс не изменились (если выбран вариант `is_migration`).

  блокировкой строки кассы (`select_for_update`);
- если не хватает — `400`:

```json
{
  "detail": "В кассе «123» 1 200,00 сом, расход 5 000,00 сом. Не хватает 3 800,00 сом.",
  "code": "cash_insufficient",
  "balance": "1200.00", "amount": "5000.00"
}
```

- обход — только с флагом `allow_negative_cash=true` и правом `can_cash_negative` (§2);
- в `GET /api/warehouse/cash-registers/` добавить поле `balance` (остаток на текущий момент) и
  `balance_at` (если передан `?date=`). Фронту колонка «Остаток» нужна в списке касс.

Существующие кассы в минусе (данные): отчёт по компаниям — касса, остаток. Ничего не исправлять
автоматически; передать владельцам.

**Приёмка:**

- [ ] Расход больше остатка → `400 cash_insufficient`, документ не проведён.
- [ ] Закуп за наличные при пустой кассе → `400 cash_insufficient` (товар не оприходован).
- [ ] Владелец с флагом проводит; сотрудник с флагом без права — `403`.
- [ ] `cash-registers/` отдаёт `balance`.
- [ ] Две параллельные выдачи по 600 при остатке 1 000: одна проходит, вторая `400`.

### B07. Проведение задним числом без ограничений

**Эндпоинты:** `PATCH /api/warehouse/documents/{id}/` (поле `date`), `post`, `unpost`.

**Как воспроизвести:** отменить проведение продажи `SALE-20261006-…` → поменять дату на
01.01.2025 → провести.
**Фактически:** проведено 01.01.2025; номер остался `SALE-20261006-…`; дата связанного денежного
документа не изменилась. Так появились, например, `SALE-20260731-0012` от 11.07.

В A14 запрещены даты **в будущем** — это работает. Прошлые даты не ограничены.

**Сделать:**

1. **Закрытие периода.** Настройка компании `closed_until` (дата). Документы с `date <= closed_until`
   нельзя проводить, отменять, редактировать и удалять без права `can_post_closed_period`:

```json
{ "detail": "Период до 30.09.2026 закрыт. Изменения запрещены.", "code": "period_closed" }
```

   Эндпоинт: `GET/PATCH /api/warehouse/settings/period-close/` → `{ "closed_until": "2026-09-30" }`,
   менять может только owner. Проверка — и по старой, и по новой дате документа.
2. **Смена даты.** Дата, отличная от сегодняшней, — только с правом `can_change_document_date`.
   Без права — `403 permission_change_date`.
3. **Связанный денежный документ.** При смене даты товарного документа менять дату его
   `MONEY_*` (если он не проведён отдельно и не в закрытом периоде).
4. **Номер.** Номер присваивается при первом проведении и больше не меняется. Чтобы номер не
   «врал», есть два варианта (решение D-B07):
   - **(рекомендация)** номер без даты: `SALE-000123` — сквозной по компании и типу;
   - номер с датой документа, перенумерация при смене даты (сложнее, ломает ссылки в печатных формах).
5. Журнал: кто и когда менял дату (`old_date`, `new_date`, `user`, `at`). Пока журнала действий нет,
   достаточно поля в документе `date_changed_by`/`date_changed_at`.

**Приёмка:**

- [ ] Сценарий выше от сотрудника без прав → `403`.
- [ ] Владелец закрыл период до 30.09 → документ от 15.09 нельзя распровести (`400 period_closed`).
- [ ] При смене даты продажи меняется дата её денежного документа.
- [ ] Номер после смены даты не противоречит дате (по выбранному варианту D-B07).

### B13. Категории платежей дублируются

**Эндпоинт:** `GET /api/warehouse/money/categories/`.

**Как воспроизвести:** провести закуп → открыть список категорий.
**Фактически:** появились вторые «Закупка», «Возврат от поставщика», «Возврат покупателю»,
«Зарплата». Дубли «Долги», «Инкассация», «Продажа» уже были раньше. Отчёты по категориям расходятся.

**Причина (предположительно):** в A2 сделаны системные категории по типу документа, но поиск
существующей категории идёт не по системному ключу (или по ключу + филиалу/складу), и при
каждом новом контексте создаётся новая.

**Сделать:**

- у категории поле `system_key` (`purchase`, `sale`, `sale_return`, `purchase_return`, `debt`,
  `incassation`, `salary`, …) и `UniqueConstraint(company, system_key)` где `system_key IS NOT NULL`;
- получение категории — `get_or_create(company=…, system_key=…)` в одном месте, под транзакцией;
- системные категории нельзя удалять и переименовывать через API (`400 category_system`);
- **миграция данных:** для каждой компании и ключа оставить одну категорию (самую старую),
  перевесить на неё все денежные документы дублей, дубли удалить. Пользовательские категории
  с тем же названием, созданные вручную, — не трогать, только отчёт.

**Приёмка:**

- [ ] Десять закупов подряд → одна категория «Закупка».
- [ ] На проде после миграции нет двух категорий с одним `system_key` в компании.
- [ ] Суммы в отчёте по категориям до и после миграции совпадают в итоге.

### B15. Оплата долга больше суммы долга

**Эндпоинт:** `POST /api/warehouse/crud/counterparties/{id}/payments/`.

**Как воспроизвести:** долг клиента 200 → «Оплатить долг» 500.
**Фактически:** проведено молча, клиент стал кредитором («Вы должны контрагенту 300»).

**Сделать:**

- если сумма > текущего долга — `400`:

```json
{
  "detail": "Долг контрагента 200,00 сом. Сумма 500,00 больше на 300,00.",
  "code": "debt_overpayment", "debt": "200.00", "amount": "500.00"
}
```

- явный режим аванса: поле `allow_advance: true` в запросе → переплата записывается как аванс

- время операции: принимать `datetime`, а не только `date` (см. B32 во фронтовой части: сейчас
  фронт шлёт только дату и время становится 00:00). Если пришла только дата — ставить текущее
  время, а не 00:00.

**Приёмка:**

- [ ] 500 при долге 200 → `400 debt_overpayment`.
- [ ] С `allow_advance=true` → проведено, сальдо −300.
- [ ] Оплата с одной датой получает текущее время.

### B16. Дубли складов и контрагентов

**Эндпоинты:** `POST /api/warehouse/crud/warehouses/`, `POST /api/warehouse/crud/counterparties/`.

**Фактически:** склад с уже существующим именем «JAY» и контрагент с тем же именем и телефоном
создаются (`201`). В базе уже «Кылым / кылым / Кылым», «Бекназар» ×2, один телефон у двух клиентов.

**Сделать:**

- **склад:** уникальность `(company, lower(trim(name)))` → `400 duplicate_warehouse`;
- **контрагент:** при совпадении нормализованного телефона (только цифры, с кодом страны `996`)
  или ИНН в компании → `400`:

```json
{
  "detail": "Контрагент с телефоном +996 555 12-34-56 уже есть: «Кылым».",
  "code": "duplicate_counterparty",
  "existing": { "id": "<uuid>", "name": "Кылым" }
}
```

  При совпадении только имени — не ошибка, а предупреждение: создавать только с
  `force_duplicate_name: true`, иначе `409 counterparty_name_exists` с тем же `existing`;
- **данные:** отчёт дублей (имя без учёта регистра, телефон, ИНН). Объединение — отдельная команда

**Приёмка:**

- [ ] Склад «jay » при существующем «JAY» → `400`.
- [ ] Контрагент с тем же телефоном в другом формате (`0555…`, `+996555…`) → `400`.
- [ ] Отчёт дублей передан владельцам.

### B08. `minimum_quantity` не сохраняется

### B11. Аналитика: неверная разбивка кассы по контрагентам

**Эндпоинт:** `GET /api/warehouse/owner/analytics/`.

### B22. Перемещение оценивается по цене продажи

**Фактически:** перемещение товара с закупкой 100 и продажей 150 — строка по 150. Старые перемещения
на 0,00 сом.

**Сделать:** при проведении `TRANSFER` ставить в строку цену = себестоимость (`purchase_price` на
момент проведения; после R15 — `cost_price`). В списке документов отдавать `warehouse_from_name` и
`warehouse_to_name`, чтобы фронт показал «откуда → куда». Старые перемещения — backfill цены
закупки (только оценка, остатки не трогать).

**Приёмка:** новое перемещение — строка по 100, сумма документа = Σ qty × 100.

### B24. ИНН не проверяется

**Фактически:** контрагент с ИНН «12» сохраняется. ИНН попадает в ЭСФ и акты сверки.

**Сделать:** если ИНН заполнен — только цифры, длина **14** (ИНН КР). Иначе
`400 {"inn": ["ИНН должен состоять из 14 цифр"]}`. Пустой ИНН — допустим. Существующие неверные —
отчёт, не исправлять автоматически. Та же проверка — для реквизитов компании.

### B30. Штрихкод с префиксом 735

**Фактически:** автоматически сгенерирован `7354625992091`; `735` — префикс GS1 Швеции, возможен
конфликт с реальными товарами при сканировании.

**Сделать:** генерировать EAN-13 во внутреннем диапазоне **`20`–`29`** (in-store, GS1), с корректной
контрольной цифрой, уникальный в компании. Рекомендуемый формат:
`2` + `0` + 10 цифр сквозного номера + контрольная цифра. Префиксы `21`–`29` не трогать: их часто
используют весы (см. B37). Существующие сгенерированные — не менять, они уже могут быть напечатаны.

### B33. Часовые пояса и номера по UTC

**Фактически:** даты приходят то с `+06:00`, то с `+00:00`. Номер формируется по UTC-дате:
`TRANSFER-20260204-0002` от 05.02 01:03 по Бишкеку.

**Сделать:**

- `TIME_ZONE = "Asia/Bishkek"`, `USE_TZ = True`; все `DateTimeField` в ответах — в `+06:00`
  (одинаково во всех сериализаторах, без ручного `isoformat()` от naive/UTC);
- дата в номере — `timezone.localdate()`, а не `date.today()` / UTC (если по D-B07 дата из номера
  не уберётся);
- фильтры `date_from` / `date_to` — по местной дате.

### B35. `cashier_password` в ответе компании

**Эндпоинт:** `GET /api/users/company/`. Поле есть в ответе (сейчас пустое). Если его заполнят,
пароль кассира увидит любой сотрудник.

**Сделать:** убрать поле из ответа (`write_only=True`). Если фронту нужно знать, задан ли пароль, —
`has_cashier_password: bool`. Пароль хранить хэшем (`make_password`), проверять отдельным эндпоинтом.

### B36. Лимиты тарифа считаются неверно

**Эндпоинт:** `GET /api/users/company/` → `limits`.
**Фактически:** `warehouses.used = 2` (факт 5), `products.used = 5` (факт ~55).

**Сделать:** `used` считать по моделям склада (`Warehouse`, `WarehouseProduct` компании, без
удалённых/архивных), а не по моделям модуля магазина. Если товар — копия в каждом складе (B31),
решить, что считать товаром для тарифа (D-B36: рекомендация — уникальные `product_group_id`).
Связано с [docs/billing/company-tariff-and-payment.md](../billing/company-tariff-and-payment.md).

### B37. Штрихкоды и весы берут товары магазина

**Фактически:** «Печать штрих-кодов» и «Интеграция с весами» запрашивают `/main/products/`
(модуль магазина). Пишется «Весовых товаров на складе нет», хотя в форме склада есть «Весовой товар».

**Сделать (бэк):** подтвердить, что `GET /api/warehouse/products/` поддерживает фильтр
`?is_weight=true` и отдаёт поля, нужные весам (PLU, единица, цена). Если PLU для складских товаров
нет — добавить `plu_code` (уникальный в компании). Переключение экранов на складские эндпоинты
сделает фронт.

### B38. Путаница в названиях цен

**Фактически:** в форме товара «Оптовая цена» сохраняется в `price`, «Цена агента» — в
`wholesale_price`. В продаже `product_wholesale_price = 0`. Из-за этого фронт отправляет
`is_wholesale: false` при выбранной «Оптовой цене» (B09), а от `is_wholesale` зависит ставка
зарплаты агента (розница 7%, опт 6%).

**Сделать (контракт, согласовать с фронтом и мобильной командой до правок):**

| Поле API | Смысл | Подпись в UI |
|---|---|---|
| `purchase_price` | цена закупки | Цена закупки |
| `price` | базовая цена продажи | Розничная цена |
| `wholesale_price` | оптовая цена | Оптовая цена |
| `agent_price` | цена для агента (новое) | Цена агента |

- миграция данных — **только по решению D-B38**: сейчас в `price` лежит то, что пользователи
  считают оптом. Варианты: (а) переименовать подписи на фронте без миграции, (б) перенести значения.
  Рекомендация — сначала (а), чтобы не сломать мобильное приложение;
- в строке продажи отдавать фактически применённую цену и тип: `applied_price`, `price_type ∈
  {retail, wholesale, agent}`; зарплату агента считать от `price_type`, а не от `is_wholesale`.
