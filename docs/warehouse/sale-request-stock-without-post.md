# Баг: проведение «Заявки на продажу» / SALE — списание остатка без успешного проведения

**Статус:** отдельный баг бэка (P0), **не** путать с кейсом SALE-20260808-0132.  
**Дата:** 2026-08-08  
**Сектор:** Склад  

---

## 0. Важно: это НЕ сегодняшний кейс SALE-20260808-0132

Сегодняшний документ `SALE-20260808-0132` (`1aa15e3c-…`) — **другой** инцидент:

| | Сегодня (другой баг) | Этот документ (баг списания) |
|---|---|---|
| Симптом | `post` → 400 «мало у агента»; склад 300→200 | Хотят провести «Заявку на продажу» — **не проводится**, но **товар со склада уже списан** |
| Причина | Нехватка agent stock + отдельно `approve`/`dispatch` cart | Подозрение: `post`/кассовый флоу списывает qty при статусе, который UI/бизнес считает «не проведён», **или** неатомарный `post` |
| Связанный тикет | [`agent-me-products-multi-warehouse.md`](./agent-me-products-multi-warehouse.md) | **Этот файл** + блок в [`backend-checklist.md`](./backend-checklist.md) |

Не закрывать баг списания ссылкой на «это была выдача агенту». Нужен отдельный прогон и фикс/подтверждение контракта.

---

## 1. Симптом (как репортят)

1. Есть документ SALE (часто с UI-лейблом **«Заявка на продажу»** = `is_sale_request` + `DRAFT`, либо уже после попытки `post`).
2. Пользователь жмёт **Провести** (`POST /warehouse/documents/{id}/post/`).
3. С его точки зрения документ **не провелся** (остался черновиком / заявкой / «не POSTED»).
4. При этом **qty на складе (или у агента) уже уменьшился**.

Ожидание бизнеса: либо документ проведён (`POSTED` или явно «ожидает кассы» с понятным статусом) **и** qty списан, либо документ не проведён **и** qty на месте.

---

## 2. Гипотезы, которые бэк обязан проверить

### H1 — `CASH_PENDING`: списание есть, `POSTED` нет (контракт)

```text
DRAFT ──post (cash)──► CASH_PENDING   ← qty уже списан
                          │
                          ├── cash/approve → POSTED
                          ├── cash/reject  → REJECTED + откат qty
                          └── unpost       → DRAFT + откат qty
```

Если так задумано — это не «тихий» баг данных, но для пользователя выглядит как «не провелась, а товар ушёл».  
**Нужно:** зафиксировать контракт в API-доке + убедиться, что `status` после `post` = `CASH_PENDING` (не `DRAFT`), и откаты работают.

### H2 — неатомарный `post` (настоящий баг данных)

```text
POST …/post/ → 4xx / 5xx / timeout
GET  document → status всё ещё DRAFT, moves пустые/частичные
GET  stock    → qty уже меньше
```

**Нужно:** одна DB-транзакция на смену статуса + movements + stock; при любой ошибке — полный rollback.

### H3 — повторный/частичный post

Первый `post` списал qty и упал после write; повторный `post` отдаёт ошибку «уже не DRAFT» / другую 4xx, UI показывает неуспех, qty не откатан.

**Нужно:** идемпотентность / ясный статус после первого успешного списания; не оставлять DRAFT после списания.

### H4 — путаница с agent-cart (исключить при разборе тикета)

`approve`/`dispatch` тоже уменьшают склад. При разборе конкретного UUID сверить timestamp списания с `approved_at` cart vs временем `post`.  
Если совпало с cart — это **не** этот баг (см. §0). Если совпало только с `post`, а status не `POSTED`/`CASH_PENDING` — баг H1–H3.

---

## 3. Что должен сделать бэк (чеклист)

### 3.1. Контракт статусов SALE / cash

- [ ] При `payment_kind=cash` и успешном `post`: ответ и БД → **`CASH_PENDING`**, не `DRAFT`, не сразу `POSTED` (если так в продукте).
- [ ] В момент перехода в `CASH_PENDING` qty уже списан — **да/нет** зафиксировать письменно.
- [ ] `cash/approve` → `POSTED` **без** повторного списания.
- [ ] `cash/reject` и `unpost` → полный откат qty.

### 3.2. Атомарность `post`

- [ ] Тест: `post` с нехваткой на 2-й позиции → 4xx, **все** qty как до вызова, `status=DRAFT`, нет лишних moves.
- [ ] Тест: исключение после write первой позиции → rollback всего.
- [ ] Тест: timeout/повторный `post` не даёт «DRAFT + уже списано».

### 3.3. SALE + `agent` + `is_sale_request`

- [ ] `post` списывает **agent stock** (не «тихо» основной склад в обход агента), если в документе указан `agent`.
- [ ] При 400 «Недостаточно у агента» — **ни** agent stock, **ни** склад компании не меняются.
- [ ] Успешный cash-`post` → `CASH_PENDING` + списание agent stock; документ не остаётся `DRAFT`.

### 3.4. Аудит

- [ ] Движения от `documents.post` и от `agent-carts.approve/dispatch` различимы (тип/reason/document_id).
- [ ] По `document_id` можно ответить: было ли списание именно этим `post`.

## 4. Минимальный тест-план (staging)

Подставить тестовые UUID.

```http
# Подготовка: DRAFT SALE, payment_kind=cash, достаточный остаток
GET  /api/warehouse/documents/{id}/
GET  /api/warehouse/products/{product_id}/          # или owner/agents/.../products/

# Проведение
POST /api/warehouse/documents/{id}/post/

# Сразу после
GET  /api/warehouse/documents/{id}/                 # status? moves?
GET  … остатки …                                   # qty изменился?
```

| # | Условие | Ожидание status | Ожидание qty |
|---|---|---|---|
| T1 | Успешный post, cash | `CASH_PENDING` | списан |
| T2 | Затем cash/approve | `POSTED` | без второго списания |
| T3 | Успешный post → cash/reject | `REJECTED` | откат |
| T4 | post при нехватке | `DRAFT` + 4xx | **без изменений** |
| T5 | post multi-item, fail на 2-й | `DRAFT` + 4xx | **без изменений** |
| T6 | post SALE+agent, мало у агента | `DRAFT` + 4xx | склад и агент **без изменений** |

Любой провал T4–T6 при уменьшенном qty = **подтверждение бага H2**.  
T1 с `status=DRAFT` при уже списанном qty = **подтверждение бага H2/H3**.  
T1 с `CASH_PENDING` + списанным qty = контракт H1 (не баг данных; нужна ясность для UI/саппорта).

## 5. Данные для поиска старых инцидентов на prod

Искать документы SALE за период жалобы:

```http
GET /api/warehouse/documents/?doc_type=SALE&… 
```

Красные флаги:

- `status=DRAFT` + непустые `moves` / связанные складские движения с этим `document_id`
- `status=DRAFT` + qty ушёл в тот же timestamp, что вызов `post` (логи), и **нет** `agent-cart` approve в ту же секунду
- два вызова `post` подряд: первый 5xx/timeout, второй 4xx, qty уже меньше

Прислать бэку: `document id`, `number`, `status`, `payment_kind`, `agent`, `is_sale_request`, `moves`, timestamp, qty до/после.
