# 25. Восстановление лида из архива

**Приоритет:** P2 — архивирование уже работает, но лид, попавший туда по
ошибке (или клиент вернулся после отказа), можно достать только через
прямой доступ к БД.
**Дата:** 12.09.2026
**Бэкенд:** новый `POST /consalting/leads/{id}/restore/`. Существующие
`POST /consalting/leads/{id}/archive/` и `GET /consalting/leads/archived/`
не меняются, кроме уточнения фильтра в §3.
**Фронт (реализовано):** `src/store/creators/funnelThunk.js` (`restoreLead`,
+ уточнён фолбэк `getArchivedLeads`), `src/Components/Sectors/Consulting/Funnel/FunnelArchiveModal.jsx`
(кнопка «↺ Восстановить» в каждой строке архива), `Funnel.jsx` (обновление
доски после восстановления).
**Связано:** [21-funnel-delete.md](./21-funnel-delete.md) (похожий паттерн
контракта — одиночное действие над лидом/воронкой).

---

## 1. Что уже было и чего не хватало

Архивирование лида уже реализовано (кнопка «В архив» в карточке лида —
появляется только когда лид дошёл до завершающей стадии воронки, `won`
или `lost`) и работает через `POST /consalting/leads/{id}/archive/`
(с фолбэком на `PATCH { is_archived: true }`, если основной эндпоинт ещё не
задеплоен). Просмотр архива — модалка «Архив завершённых лидов»
(`FunnelArchiveModal.jsx`), список — `GET /consalting/leads/archived/`.

Чего не было: **обратного действия**. Архивный лид нельзя было вернуть —
ни на фронте не было кнопки, ни на бэке эндпоинта. Единственный обходной
путь — редактировать лид напрямую в БД, что и попросили закрыть этим
тикетом: «добавить возможность архивировать лида и обратно возвращать».

## 2. Требование: «когда вернул — должен быть в воронке и сразу быть в работе»

Разобрал формулировку на два конкретных условия:

1. **«В воронке»** — карточка должна снова появиться на доске (сейчас
   архивные лиды с доски исключены — иначе архив не имел бы смысла). Значит
   восстановление обязано снять `is_archived`.
2. **«Сразу быть в работе»** — не просто «видна», а на **активной** стадии,
   с которой можно продолжать работу. Архивируется лид **после** того, как
   дошёл до завершающей стадии (`won`/`lost`) — если просто снять
   `is_archived` и ничего больше, карточка вернётся на доску, но так и
   останется висеть в колонке «Успешно»/«Отказ», что для менеджера
   выглядит как «уже закрыто», а не «надо разобрать».

Поэтому `restore` — это не голый `is_archived: false`, а комбинация трёх
полей: снять флаг архива, сбросить `status` с `won`/`lost` в рабочий, и
переставить `stage` на активную (не терминальную) стадию воронки.

## 3. Контракт

### 3.1. `POST /consalting/leads/{id}/restore/`

```
POST /consalting/leads/{id}/restore/
{ "stage": "<uuid стадии>" }   // необязательно
```

Ответ — обновлённый объект лида (тот же формат, что у `archive`/`transfer`).

Поведение:

1. `Lead.is_archived = False`.
2. `Lead.status` → рабочий статус (`"in_progress"` либо аналог — как у
   свежесозданного лида в активной работе; **не** `won`/`lost`/`archived`).
3. `Lead.stage`:
   - если `stage` передан в теле — берём его, но **проверяем**, что он
     принадлежит той же воронке и не является терминальной стадией
     (`stage_type` не `won`/`lost` — если `FUNNEL_V2` со стадиями типов
     включён) → иначе `400`;
   - если `stage` не передан — подставляем **первую не терминальную стадию
     воронки** (`Stage.objects.filter(funnel=lead.funnel, is_terminal=False).order_by("order").first()`)
     — по аналогии с тем, как `target_stage: null` в
     `POST /leads/{id}/transfer/` подставляет первую стадию воронки (см.
     [22 §4.2](./22-bulk-lead-transfer.md)).
   - если у воронки вообще нет нетерминальных стадий (вырожденный случай,
     напр. однaстадийная воронка) — оставить текущую стадию, не падать
     ошибкой.
4. `Funnel.leads_count` (и счётчик соответствующей колонки) пересчитывается
   консистентно — та же оговорка, что в [20](./20-funnel-leads-count-stale.md)
   и [22 §4.4](./22-bulk-lead-transfer.md).
5. Доступ — тот же, что на `archive`/`transfer`: `canManageLeadsInFunnel`
   (owner/admin/rop без ограничений, supervisor/сотрудник — только если
   может редактировать этот лид, см. [12 §5](./12-regional-supervisor-rbac.md)).
6. Повторный `restore` уже не архивного лида → `400 "Лид не в архиве"`
   (идемпотентность не нужна — это явное пользовательское действие по
   кнопке, не фоновая задача).

### 3.2. Пока `restore` не задеплоен — фронтовый фолбэк

Если `POST /leads/{id}/restore/` отвечает `404`/`501`, фронт (как и для
`archive`/`transfer`) сам собирает то же самое через:

```
PATCH /consalting/leads/{id}/
{ "is_archived": false, "status": "in_progress" }
```

**Без** попытки подобрать активную стадию на фронте (это требует знать
структуру стадий воронки, которую фронт для архивных лидов не всегда имеет
загруженной) — то есть в фолбэк-режиме лид вернётся на доску, но может
остаться в исходной (терминальной) стадии до тех пор, пока сам эндпоинт
`restore` не будет задеплоен. Это ожидаемое временное ограничение фолбэка,
не финальное поведение — приоритет бэку сделать сам `POST .../restore/`,
а не полагаться на PATCH-фолбэк для стадии.

### 3.3. Уточнение фильтра архива (§ обновлено в этом тикете)

`GET /consalting/leads/archived/` — без изменений в контракте, но
фолбэк-путь на фронте (`GET /leads/?is_archived=true&status=won`) убрал
жёсткий `status=won` — раньше проигранные (`lost`) архивные лиды не
попадали в список архива при недоступном основном эндпоинте. Если основной
`GET /leads/archived/` на бэке сам фильтрует по `status=won` где-то внутри —
это тоже стоит проверить и убрать: архив должен показывать оба терминальных
статуса.

## 4. Что уже делает фронт

- Модалка архива (`FunnelArchiveModal.jsx`) — кнопка «↺ Восстановить» в
  каждой строке (без открытия карточки, `stopPropagation`), вызывает
  `restoreLead({ id })` **без** явной стадии — доверяет бэку выбрать первую
  активную стадию воронки, как описано в §3.1.
- По успеху — строка убирается из списка архива на месте (без перезагрузки
  всего списка), и родительский `Funnel.jsx` обновляет доску воронки, куда
  вернулся лид (`refreshBoard(funnelId)`), плюс показывает уведомление «Лид
  восстановлен из архива и снова в работе».
- По ошибке — текст ошибки показывается в модалке архива, строка остаётся
  (retry по той же кнопке).

## 5. Не в этой итерации

- Выбор целевой стадии восстановления вручную на фронте (сейчас всегда
  «первая активная стадия по умолчанию» — бэк её сам подставляет). Если
  понадобится ручной выбор — добавить select аналогично
  `BulkMoveFunnelModal.jsx` §7.2 из [22](./22-bulk-lead-transfer.md).
- Массовое восстановление нескольких архивных лидов разом — архив сейчас
  не поддерживает множественный выбор, только по одному.
- История «когда и кем восстановлен» отдельной лентой активности — если
  нужна, `restore` должен писать запись в timeline лида (как `win`/`lose`),
  это на усмотрение бэка при реализации.

## 6. Чек-лист приёмки

- [ ] `POST /leads/{id}/restore/` без `stage` — лид снимается с архива,
      статус меняется на рабочий, стадия — первая нетерминальная стадия
      воронки.
- [ ] `POST /leads/{id}/restore/` с валидным `stage` своей воронки —
      применяется именно эта стадия.
- [ ] `stage` чужой воронки или терминальной стадии → `400`.
- [ ] Повторный `restore` уже не архивного лида → `400`.
- [ ] После восстановления карточка видна на доске воронки в активной
      колонке (не «Успешно»/«Отказ»).
- [ ] `Funnel.leads_count`/счётчики колонок консистентны после восстановления.
- [ ] Доступ ограничен так же, как `archive`/`transfer` — чужой лид вне
      прав вызывающего → `403`.
- [ ] `GET /leads/archived/` (и фолбэк) отдают и `won`, и `lost` архивные
      лиды, не только `won`.
