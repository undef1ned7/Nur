# 20. `Funnel.leads_count` рассинхронизирован с реальным числом лидов на доске

**Приоритет:** P2 — не ломает функциональность (карточки лидов никуда не
пропадают), но искажает счётчики в UI и вводит в заблуждение.
**Дата:** 12.09.2026
**Бэкенд:** сериализатор `Funnel` (поле `leads_count`), эндпоинты
`GET /consalting/funnels/` и `GET /consalting/funnels/{id}/board/`.
**Фронт (воркэраунд применён):** `src/Components/Sectors/Consulting/Funnel/Funnel.jsx`
— бейджи с числом лидов на вкладках воронок.

---

## 1. Проблема

В **одном и том же ответе** `GET /consalting/funnels/{id}/board/` бэкенд
отдаёт два разных числа лидов для одной воронки, и они не совпадают:

```
GET /consalting/funnels/2baf617c-45e1-40d1-9aaf-bb75f9ee9603/board/
```

```jsonc
{
  "funnel": {
    "id": "2baf617c-45e1-40d1-9aaf-bb75f9ee9603",
    "name": "Основная воронка",
    "is_main": true,
    "leads_count": 3            // ← застряло, не пересчитывается
  },
  "totals": { "count": 43, "amount": 0.0 },   // ← реальное число карточек
  "columns": [ /* … суммарно 41 лид в колонках … */ ],
  "unassigned": [ /* … 2 лида … */ ]
}
```

Проверка: `len(columns[].leads) + len(unassigned) == 43`, что совпадает с
`totals.count`, но **не совпадает** с `funnel.leads_count == 3`.

То же поле `leads_count` (уже без расхождения по факту, но потенциально
подвержено той же болезни) отдаётся и в плоском списке `GET
/consalting/funnels/` — то есть бэкенд хранит `leads_count` как
денормализованное поле на модели `Funnel`, которое обновляется от случая к
случаю (скорее всего — только в момент создания воронки или отдельных
операций), а не пересчитывается при каждом изменении набора лидов
(перенос между воронками, `redistribute`, создание нового лида и т.д.).

## 2. Как обнаружено

Пользователь заметил на `/crm/consulting/funnel`, что переключатель
«Все» в тулбаре показывает **83**, хотя на вкладках воронок сумма видимых
бейджей была заметно меньше (бейдж «Основная воронка» показывал **3**).
Прямой запрос к API (см. §1) подтвердил: фронтовый счётчик «Все» считает
честно — суммирует реальные карточки лидов из уже загруженных досок
(`columns[].leads` + `unassigned`) по всем видимым воронкам, — а бейдж на
вкладке брал `funnel.leads_count` из ответа, который на бэке не
актуализирован.

Полная раскладка на момент проверки (компания `e3dbc253-…`):

| Воронка | `funnel.leads_count` (бейдж) | `totals.count` (факт) |
|---|---|---|
| Основная воронка | **3** | **43** |
| Бишкек | 19 | 19 |
| ОШ | 19 | 19 |
| Отдел внедрения и обучение | 2 | 2 |
| 5 ролевых воронок (пустые) | 0 | 0 |

Расхождение — только у «Основной воронки» (самая активная, туда чаще всего
переносятся/создаются лиды вручную и через `redistribute`), что указывает на
проблему именно с **пересчётом при изменении состава лидов**, а не с полем
как таковым.

## 3. Что нужно на бэкенде

1. Либо пересчитывать `Funnel.leads_count` при каждой операции, меняющей
   принадлежность лида воронке (`create`, `transfer`, `redistribute`,
   `win`/`lose` если они не убирают лид с доски, удаление лида) —
   транзакционно, в той же операции, что меняет `Lead.funnel`.
2. Либо (надёжнее и проще) **не хранить `leads_count` как отдельное поле
   вовсе**, а всегда считать его на лету в сериализаторе — так же, как уже
   считается `totals.count` в `board/`. Это гарантирует, что два числа в
   одном ответе никогда не разъедутся, потому что будут одним и тем же
   вычислением.
3. В `GET /consalting/funnels/` (плоский список, без `board/`) число тоже
   должно быть живым — иначе тот же баг всплывёт там, где фронт пока не
   подставляет `totals.count` (там его просто нет в этом эндпоинте).

## 4. Фронтовый воркэраунд (применён 12.09.2026)

В `Funnel.jsx` бейджи с числом лидов на вкладках воронок и подворонок
переключены на `board.totals.count` с фолбэком на `board.funnel.leads_count`,
если `totals` по какой-то причине отсутствует:

```js
const count = fb?.totals?.count ?? fb?.funnel?.leads_count;
```

Это устраняет видимое расхождение в UI (бейдж «Основная воронка» теперь
показывает 43, как и переключатель «Все»), но **не исправляет источник** —
если `GET /consalting/funnels/` (плоский список, без `totals`) где-то ещё
используется для отображения числа лидов, там расхождение останется видимым
до фикса на бэке.

## 5. Повторное подтверждение 14.09.2026 — баг глубже, чем счётчик

**Компания:** `e3dbc253-…` (та же). Прямой прод-запрос:

```
GET /consalting/funnels/2baf617c-.../board/   (Основная воронка, is_main=true)
```

`totals.count = 72`, бейдж на вкладке — тоже 72. Но детальная выгрузка
`GET /consalting/funnels/2baf617c-.../` (без `board/`) показывает **честную**
сумму по своим стадиям: `16 + 0 + 2 = 18`. И прямой запрос
`GET /consalting/leads/?funnel=2baf617c-...` возвращает **18** карточек с
`channel=manual` — это реальные лиды, которые лежат в главной воронке.

Расхождение (72 вместо 18) — **не только в поле `leads_count`**. Первая
колонка `board().columns[0].leads` буквально содержит 70 карточек лидов, из
которых по полю `lead.funnel` видно, что они принадлежат **другим**
воронкам:

| `lead.funnel` (реальная воронка лида) | Карточек попало в колонку «Основной» |
|---|---|
| ОШ (`6cdb0ea7…`) | 25 |
| Бишкек (`2e7a026b…`) | 24 |
| Основная (`2baf617c…`, честные) | 16 |
| Хузайфа — подворонка Оша (`cdd8b772…`) | 2 |
| Отдел внедрения и обучение (`0a278f52…`) | 2 |
| Руководитель отдела внедрения (`70bbad25…`) | 1 |

Т.е. `board()` для `is_main`-воронки не просто отдаёт устаревшее число — он
**подмешивает в `columns[].leads` карточки лидов из всех остальных воронок
компании** в первую (intake) колонку, и `totals.count` честно считает этот
уже загрязнённый набор (72 = реальная сумма всех лидов компании).
Фронтовый воркэраунд §4 (`totals.count ?? funnel.leads_count`) здесь
**не помогает** — оба числа одинаково завышены, потому что сам список карточек
уже неверный, а не только денормализованный счётчик.

**Вывод для бэка:** видимо, `board()` для воронок с `is_main=true` по ошибке
не фильтрует лиды по `lead.funnel == funnel.id` (возможно, исторический
пережиток модели 1A, где главная воронка была «диспетчером» и агрегировала
все лиды компании — см. [06 §2](./06-regional-funnels-routing.md), но после
включения `regional-funnel-routing.enabled=true` это поведение больше не
должно применяться). Нужно: `board()` для main-воронки — как для любой
другой — должен возвращать **только** лиды с `lead.funnel_id == funnel.id`;
компанийный агрегат (все лиды) — отдельный эндпоинт/параметр, если он вообще
нужен фронту (сейчас фронт сам считает «Все» суммированием досок, см. §2).

Побочный эффект для пользователя: региональное распределение на самом деле
работает почти поровну (Бишкек 24 / Ош 25 — 2 активных региона, третий,
Джалал-Абад, в `regional-funnel-routing.rules` не настроен), просто бейдж
«Основная воронка» вводит в заблуждение, будто там 72 нераспределённых лида.

## 6. Чек-лист приёмки

- [ ] `funnel.leads_count` в `GET /consalting/funnels/{id}/board/` всегда
      равен `totals.count` в том же ответе.
- [ ] После `redistribute`, `transfer`, ручного создания/удаления лида —
      `leads_count` воронки в `GET /consalting/funnels/` обновляется
      немедленно (без дополнительного действия вроде пересоздания воронки).
- [ ] Проверено на воронке с большим количеством лидов (как «Основная»,
      где багу было проще всего проявиться) — не только на маленьких
      региональных воронках, где расхождения не было и баг было бы легко
      пропустить.
- [ ] `board()` для `is_main`-воронки возвращает в `columns[].leads` только
      карточки с `lead.funnel_id == funnel.id` — ни одной карточки с
      `lead.funnel` от другой воронки (см. §5, было 70/72 чужих).
