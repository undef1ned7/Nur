# 21. Удаление воронки: право автора-сотрудника на свою подворонку + контракт `409`

**Приоритет:** P2 — расширение прав (без этого сотрудники физически не могут
удалить заведённую ими же тестовую/лишнюю подворонку, только owner/admin).
**Дата:** 12.09.2026
**Бэкенд:** `DELETE /consalting/funnels/{id}/`.
**Фронт (реализовано):** `src/utils/consultingFunnelAccess.js`
(`canDeleteFunnel`), `src/Components/Sectors/Consulting/Funnel/FunnelBoardRow.jsx`,
`src/Components/Sectors/Consulting/Funnel/Funnel.jsx` (`onDeleteFunnel`).
**Связано:** [17-employee-region-subfunnels.md §17.7](./17-employee-region-subfunnels.md#177-patch-consalting-funnelsid).

---

## 1. Задача

Уже описано в [17 §17.7](./17-employee-region-subfunnels.md), но не было
явно вынесено в отдельный контракт с примерами ответов — делаем здесь, чтобы
у бэкенда была точная спека на удаление.

Сейчас (до этого тикета) на фронте кнопка «Удалить» у воронки показывалась
только `owner/admin/rop`. Обычный сотрудник, даже создав **свою** подворонку
(`funnel_kind: "employee"`, `owner_user: <он>`, см. [17 §17.2](./17-employee-region-subfunnels.md)),
не мог её удалить — только руководство. Это неудобно: сотрудник заводит
тестовую/ошибочную подворонку и не может сам её убрать.

## 2. Матрица прав на удаление

| Кто | Может удалить |
|---|---|
| `owner` / `admin` / `rop` | любую воронку, кроме `main`/`is_static` — **включая ролевые** (см. §7, добавлено 12.09.2026) |
| `supervisor` | **только свою** подворонку (`owner_user == он сам`) — в этой итерации трактуется как обычный сотрудник, **не** как региональное руководство. Расширение права до «любая подворонка сотрудника своего региона» — не в этом тикете, см. §6 |
| сотрудник (`salesperson` и т.д.) | **только свою** подворонку (`owner_user == он сам`); ролевую воронку своей же роли — **не может**, только owner/admin/rop |
| кто угодно — чужую подворонку | `403` |
| кто угодно — `main`/`is_static` воронку | `403` (защищены всегда, независимо от роли — это ядро маршрутизации, см. [06](./06-regional-funnels-routing.md)) |

Это симметрично матрице `PATCH` из [17 §17.7](./17-employee-region-subfunnels.md#177-patch-consalting-funnelsid):
`owner_user` не даёт прав менять `parent_funnel`, но даёт право удалить всю
воронку целиком, если внутри нет незакрытых лидов.

## 3. Условие удаления: нет незакрытых лидов

```
DELETE /consalting/funnels/{id}/
```

**Успех** (лидов нет или все `converted`/`rejected`):

```
204 No Content
```

**Отказ** (есть лиды в статусах, отличных от `converted`/`rejected`):

```jsonc
// 409 Conflict
{
  "detail": "В воронке есть 5 незакрытых лид(ов). Перенесите или закройте их перед удалением."
}
```

Фронт (`Funnel.jsx` → `onDeleteFunnel`, [Funnel.jsx:484-508](../../../src/Components/Sectors/Consulting/Funnel/Funnel.jsx))
уже показывает `detail` из ответа пользователю как есть — **обязательно**
возвращать читаемый текст на русском в `detail`, а не только код ошибки,
иначе пользователь увидит нечитаемый JSON.

**Отказ по правам** (сотрудник пытается удалить чужую/защищённую воронку):

```jsonc
// 403 Forbidden
{ "detail": "Нет прав на удаление этой воронки." }
```

## 4. Реализовано на фронте (эта итерация)

- `canDeleteFunnel(profile, funnel)` в `utils/consultingFunnelAccess.js` —
  `true` для owner/admin/rop на любой незащищённой воронке **и** для автора
  подворонки (`getFunnelOwnerUserId(funnel) === текущий пользователь`).
- Кнопка «Удалить» в `FunnelBoardRow.jsx` показывается по этому праву, а не
  только `isManager`.
- Ошибка `409` показывается пользователю текстом из `detail`; если бэк вдруг
  не пришлёт `detail` — фронт подставляет свой fallback-текст с советом
  перенести/закрыть лиды.

**Важно**: фронт **не проверяет** заранее число открытых лидов перед показом
кнопки/подтверждения — источник истины полностью на бэке (`409`). Это
осознанно: дублировать подсчёт на фронте — лишняя точка рассинхрона (см.
[20-funnel-leads-count-stale.md](./20-funnel-leads-count-stale.md), где как
раз показано, к чему приводит расхождение подсчётов лидов между фронтом и
бэком).

## 5. Чек-лист приёмки

- [ ] Сотрудник, создавший свою подворонку, может её удалить через
      `DELETE /consalting/funnels/{id}/`, если в ней нет незакрытых лидов.
- [ ] Тот же сотрудник получает `403` при попытке удалить подворонку
      **другого** сотрудника (тот же регион).
- [ ] Тот же сотрудник получает `403` при попытке удалить `main`/ролевую/
      региональную воронку.
- [ ] Воронка с открытыми лидами → `409` с понятным `detail` на русском,
      указывающим количество незакрытых лидов.
- [ ] После переноса/закрытия всех лидов повторный `DELETE` той же воронки
      → `204`.
- [ ] `owner`/`admin`/`rop` — поведение не изменилось (могут удалять любые
      незащищённые воронки, включая чужие подворонки сотрудников).
- [ ] `supervisor` может удалить только СВОЮ подворонку (если она у него
      есть) — подворонки сотрудников своего региона удалить **не может**
      (эта итерация не расширяет его права до регионального масштаба, см. §6).

## 6. Не в этой итерации

Отдельный вопрос (не реализован ни на фронте, ни описан здесь как
обязательный): должен ли `supervisor` иметь право удалять подворонки **любых
сотрудников своего региона** (не только свою), по аналогии с тем, как он уже
видит и управляет их лидами ([12 §5](./12-regional-supervisor-rbac.md)).
Если да — на фронте потребуется расширить `canDeleteFunnel` условием
`isConsultingRegionalSupervisor(profile) && region(funnel) ∈ me`, а на бэке —
добавить это в матрицу прав `DELETE`. Заводить отдельным тикетом, если
понадобится.

## 7. Удаление ролевых воронок (добавлено 12.09.2026)

### Что такое ролевая воронка

Каждой **кастомной роли** сотрудника (создаётся в «Сотрудники → Роли →
Создать роль», см. `Teachers.jsx` → `submitRoleCreate` →
`provisionFunnelForCustomRole`) автоматически заводится **своя воронка**
(`custom_role: <id роли>`, 3 системные стадии: «Новые заявки» / «В работе» /
«Завершено»). Это рабочая доска для всех сотрудников с этой ролью — по
умолчанию продавец с изолированным доступом (`shouldIsolateConsultingByOwner`)
видит **только** воронку своей роли (+ основную, если не в режиме изоляции) и
работает только со своими лидами внутри неё
(`filterFunnelsForUser` → `resolveCustomRoleId(f) === customRole`).

Пример: роль «Таргетолог» → воронка «Таргетолог» с теми же 3 стадиями;
все сотрудники с ролью «Таргетолог» видят и ведут лиды в этой воронке.

### Почему раньше было нельзя удалить

Ролевая воронка была в списке защищённых (`isProtectedFunnel`) наравне с
основной — исторически, чтобы случайно не снести рабочую доску целого
отдела. Но роли создаются и упраздняются регулярно (реорганизация,
переименование отделов), а воронка от старой роли раньше оставалась
«вечным мусором» без возможности удаления через UI.

### Что изменилось

- `owner/admin/rop` теперь могут удалить ролевую воронку — как и любую
  другую незащищённую (см. §2). Защищена от удаления осталась только
  `main`/`is_static`.
- Сотрудники **не могут** удалить ролевую воронку своей же роли — только
  owner/admin/rop, аналогично тому, что только они управляют самими ролями.
- Переименование ролевой воронки (`PATCH` меты) **по-прежнему запрещено**
  всем — имя синхронизировано с названием роли, отдельное переименование
  воронки создало бы рассинхрон. Меняется это через переименование самой
  роли (`Teachers.jsx` → «Роли» → редактировать), не через воронку.
- Фронт перед удалением ролевой воронки показывает отдельное предупреждение
  (`Funnel.jsx` → `onDeleteFunnel`):

  > Удалить воронку роли «…»? Это действие необратимо. Все сотрудники с этой
  > ролью потеряют доступ к своей рабочей доске — сначала переведите роль
  > сотрудников на другую роль или перенесите их лиды.

  Фронт **не блокирует** удаление, если у роли ещё есть сотрудники или лиды
  — это чисто предупреждающий текст. Реальная защита (нельзя удалить с
  открытыми лидами) — по-прежнему только через `409` с бэка (см. §3).

### Что нужно на бэке

- `DELETE /consalting/funnels/{id}/` для ролевой воронки (`custom_role !=
  null`) должен работать так же, как для обычной custom-воронки: `204` при
  отсутствии незакрытых лидов, `409` с `detail` — если есть.
- **Роль (`/users/roles/custom/{id}/`) при этом не удаляется** — это два
  независимых объекта. Если роль осталась без воронки, сотрудники этой роли
  временно теряют видимую доску (пока не создадут новую воронку под эту же
  роль вручную, или роль не поменяют/удалят отдельно). Это ожидаемое,
  осознанное поведение этой итерации — на бэке ничего каскадно удалять/
  создавать не нужно.
- Если у бэка есть отдельная защита конкретно на `custom_role != null` в
  DELETE-хендлере (раньше не пускавшая никого) — её нужно снять для
  owner/admin/rop, сохранив для остальных ролей запрос.

### Чек-лист приёмки (§7)

- [ ] `owner`/`admin`/`rop` могут удалить ролевую воронку без открытых лидов
      → `204`.
- [ ] Ролевая воронка с открытыми лидами → `409` с понятным `detail`
      (как для обычной воронки, см. §3).
- [ ] Сотрудник с ролью, для которой существует воронка, получает `403` при
      попытке её удалить (даже если он единственный в этой роли).
- [ ] После удаления ролевой воронки сама роль (`/users/roles/custom/{id}/`)
      остаётся существовать — `DELETE` воронки не удаляет и не блокирует
      роль.
- [ ] `main`/`is_static` воронку по-прежнему нельзя удалить никому.
