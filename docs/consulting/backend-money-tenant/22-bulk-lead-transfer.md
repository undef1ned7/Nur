# 22. Массовые действия с лидами (с доски воронки)

**Приоритет:** P1 — ручной разбор пула/входящих лидов десятками карточек
одну за другой занимает неоправданно много времени у владельца/руководителя.
**Дата:** 12.09.2026, дополнено 12.09.2026 (§7 — массовый перевод на стадию
и массовый перенос в воронку).
**Бэкенд:** `POST /consalting/leads/{id}/transfer/`, `POST
/consalting/leads/{id}/assign/`, `POST /consalting/leads/{id}/move-stage/` —
все три уже существуют (см. [12
§5](./12-regional-supervisor-rbac.md#5-матрица-доступа-обязательно-на-сервере),
[backend-main-funnel-inbound.md §5](../backend-main-funnel-inbound.md#5-transfer-на-другую-воронку-явный)).
Новых эндпоинтов эта задача **не** вводит — фронт просто вызывает
существующие в цикле по выбранным лидам.
**Фронт (реализовано):**
`src/Components/Sectors/Consulting/Funnel/BulkAssignLeadsModal.jsx` (передача
сотруднику), `BulkMoveStageModal.jsx` (перевод на стадию, §7.1),
`BulkMoveFunnelModal.jsx` (перенос в воронку, §7.2), `bulkLeadOps.js` (общий
`runWithConcurrency` для всех трёх), `FunnelBoardRow.jsx` (чекбоксы на
карточках), `Funnel.jsx` (панель массовых действий с тремя кнопками).
**Связано:** [17-employee-region-subfunnels.md](./17-employee-region-subfunnels.md)
(воронки сотрудников), [21-funnel-delete.md](./21-funnel-delete.md).

## 1. Что попросили и что это значит на практике

Формулировка задачи: «массовая передача лидов в воронку сотрудника, и эти
лиды должны стать его для руководителя».

Разобрал на два независимых требования, потому что не у каждого сотрудника
есть собственная подворонка (это опциональная фича из
[17](./17-employee-region-subfunnels.md), сотрудник должен сам её завести
через «+ Воронка», если у него есть право `can_create_funnel`):

1. **«Стать его для руководителя»** — обязательное условие. Руководитель
   видит владельца лида по полю `Lead.owner`, не по тому, в какой воронке
   лид лежит. Значит минимум, что нужно всегда — `owner = <сотрудник>`.
2. **«Передать в воронку сотрудника»** — выполняется, **если** у сотрудника
   такая воронка есть. Если нет — физически переносить лид некуда
   (создавать воронку за сотрудника без его ведома — плохой UX и не
   предусмотрено правами: подворонку создаёт **сам** сотрудник, см. [17
   §17.3](./17-employee-region-subfunnels.md#173-право-can_create_funnel)).

Поэтому реализация — гибридная: смотрим, есть ли у выбранного сотрудника
своя подворонка (`Funnel.owner_user === сотрудник`); если есть — **переносим**
лид в неё через `transfer` (и сразу же в этом вызове проставляем `owner`);
если нет — просто **переназначаем** через `assign` (лид остаётся в текущей
воронке, но `owner` меняется, руководитель видит его как «лид сотрудника Х»
в фильтре по ответственному).

## 2. Почему это безопасно опереться на уже существующие `transfer`/`assign`

Разобрал два существующих файла перед тем как писать код:

### `backend-main-funnel-inbound.md` §5 — `transfer` меняет тот же лид, не клонирует

```
`transfer` / «В другую воронку» — ручной продуктовый шаг (например main →
SMM после квалификации).
- Меняет `Lead.funnel` (+ стадия целевой воронки).
- `owner` сохраняется или задаётся явно в payload.
- Inbound `lead` FK тот же.
```

Это прямо разрешает передавать `owner` в теле `POST /leads/{id}/transfer/` —
то есть перенос в подворонку сотрудника и назначение владельца происходит
**одним запросом**, без гонки между двумя отдельными вызовами.

> ⚠️ В `src/store/creators/funnelThunk.js` рядом с `transferLeadToFunnel` есть
> комментарий «копия на основе исходного» — это неточность в комментарии:
> относится только к **fallback**-ветке (когда `/transfer/` отвечает 404/501
> и фронт клонирует лид вручную через `POST /leads/`). Основной путь —
> `POST /leads/{id}/transfer/` — меняет тот же самый `Lead`, как и описано в
> `backend-main-funnel-inbound.md §5`. Стоит поправить комментарий в коде
> отдельным мелким PR, чтобы не вводить в заблуждение в будущем.

### `12-regional-supervisor-rbac.md` §5 — матрица доступа уже покрывает bulk-сценарий

`POST /leads/{id}/assign/`, `/claim/`, `/transfer/` — доступны owner/admin/rop
«без ограничений», supervisor — «в пределах своих регионов», `transfer` в
чужой регион — `403`. Массовая передача — это просто N вызовов одного и того
же уже описанного эндпоинта, права те же, отдельная матрица не нужна.

## 3. Алгоритм фронта (что уже сделано)

### 3.1. Выбор лидов

На доске воронки ([FunnelBoardRow.jsx](../../../src/Components/Sectors/Consulting/Funnel/FunnelBoardRow.jsx))
у каждой карточки, если `canManageLeadsInFunnel` разрешает (менеджер, или
сотрудник/руководитель с грантом на воронку), появляется чекбокс. Клик по
чекбоксу не запускает открытие карточки/drag (`stopPropagation`).

Выбор — `Set<leadId>`, живёт в `Funnel.jsx`, сбрасывается при переключении
активной воронки (`useEffect` на `activeFunnel.id`) — чтобы не пытаться
переносить лид из воронки, которая уже не открыта на экране.

### 3.2. Панель массовых действий

Когда выбран хотя бы один лид — внизу экрана всплывает панель:
«Выбрано N лидов» + кнопки «Передать сотруднику» / «Снять выбор».

### 3.3. Модалка `BulkAssignLeadsModal`

1. Грузит **всех** сотрудников компании (`GET /users/employees/`) — не
   ограничивает списком сотрудников текущей воронки/региона в этой
   итерации (см. §6 — сознательно не в этой итерации).
2. Строит карту `owner_user → Funnel` по уже загруженному списку видимых
   воронок (`funnels`, доступных вызывающему), чтобы показать в выпадашке,
   у какого сотрудника уже есть своя воронка.
3. По кнопке «Передать» — параллельно (не больше 4 одновременных запросов,
   `runWithConcurrency`) на каждый `leadId`:
   - если у сотрудника есть своя воронка → `transferLeadToFunnel({ id,
     target_funnel: <его воронка>, target_stage: null, owner: <сотрудник> })`;
   - иначе → `assignLead({ id, owner: <сотрудник> })`.
4. Собирает результат (`ok`/`fail`), показывает сводку. При частичных
   ошибках модалка не закрывается автоматически — пользователь видит,
   сколько прошло, сколько нет, и закрывает вручную (retry по уже успешно
   перенесённым лидам не исключён — известное ограничение, см. §6).
5. По завершении без ошибок — обновляет доски (исходную и, если был перенос,
   воронку сотрудника) и очищает выбор.

## 4. Что нужно ПРОВЕРИТЬ на бэке (это не новая разработка, а верификация контракта)

Так как отдельного bulk-эндпоинта не вводится, тут не контракт для
реализации, а чек-лист для верификации, что существующие `transfer`/`assign`
действительно ведут себя так, как описано в уже существующих доках (§2), под
нагрузкой массового вызова:

1. `POST /leads/{id}/transfer/` с `{ target_funnel, target_stage: null,
   owner: "<uuid>" }` — принимает `owner` в теле и сразу его проставляет
   (не только после отдельного `assign`).
2. `target_stage: null` → бэк сам подставляет первую стадию целевой воронки
   (сериализатор не должен требовать `target_stage` обязательным).
3. Параллельные `transfer`/`assign` по РАЗНЫМ `id` (до 4 одновременно) не
   создают гонок/дедлоков — каждый лид меняется независимо.
4. `Funnel.leads_count` целевой и исходной воронки пересчитывается
   консистентно после каждого переноса — иначе воспроизведётся баг из
   [20-funnel-leads-count-stale.md](./20-funnel-leads-count-stale.md), но
   теперь массово, а не на одном лиде.
5. Ответ `transfer`/`assign` на лид без прав (например, лид другого
   региона у supervisor) — `403` с понятным `detail`, чтобы `result.fail`
   на фронте не был немой цифрой без объяснения.

## 5. Чек-лист приёмки (фронт, для регресс-теста)

- [ ] На доске воронки у карточек появляется чекбокс только там, где есть
      право управлять лидами (`canManageLeadsInFunnel`).
- [ ] Выбор нескольких карточек показывает панель «Выбрано N лидов» с
      правильным числом.
- [ ] Переключение на другую вкладку воронки сбрасывает выбор.
- [ ] «Передать сотруднику» → сотруднику **со своей воронкой**: все выбранные
      лиды переезжают в его воронку, `owner` = он, исходная и целевая доски
      обновляются без перезагрузки страницы.
- [ ] «Передать сотруднику» → сотруднику **без своей воронки**: лиды
      остаются в текущей воронке, `owner` меняется, карточки видно в фильтре
      «Ответственный = этот сотрудник».
- [ ] Частичная ошибка (например, один лид уже в терминальном статусе) —
      модалка показывает `N передано, M с ошибкой`, не закрывается сама.
- [ ] После успешной массовой передачи выбор снят, панель скрыта.
- [ ] §7.1 «На стадию»: выбор стадии из списка стадий **текущей открытой
      воронки**, все выбранные лиды переходят в неё, доска обновляется.
- [ ] §7.1 Кнопка «На стадию» неактивна (`disabled`), если у воронки нет ни
      одной стадии (`boardsMap[funnelId].columns` пуст).
- [ ] §7.2 «В другую воронку»: список целевых воронок не включает текущую
      открытую; выбор стадии необязателен (по умолчанию — первая стадия
      целевой воронки); `owner` лидов не меняется.
- [ ] §7.2 После переноса обновляются **обе** доски — исходная и целевая.
- [ ] Обе новые операции показывают `N перенесено, M с ошибкой` при частичном
      сбое и не закрывают модалку автоматически (тот же UX, что у «Передать
      сотруднику»).

## 6. Не в этой итерации (сознательно)

- **Список сотрудников не фильтруется по региону выбранных лидов** — в
  отличие от `AssignLeadModal.jsx` (назначение одного лида региону-скоуп).
  При большом штате это может быть неудобно; фильтрацию по
  `consulting_region_codes` стоит добавить отдельным пунктом, если
  понадобится.
- **Retry по частично проваленной пачке** — при повторном клике «Передать»
  после ошибки фронт отправит запрос по **всем** изначально выбранным
  `leadId`, включая уже успешно перенесённые (они просто ещё раз пройдут
  `transfer`/`assign` с тем же результатом — идемпотентно, но не оптимально).
  Разделять «успешные» и «проваленные» для точечного повтора — не в этой
  итерации.
- **Bulk-создание подворонки за сотрудника прямо из этой модалки** (если у
  него её ещё нет) — сознательно не делаем: подворонку должен заводить сам
  сотрудник (право `can_create_funnel`), иначе ломается модель владения из
  [17](./17-employee-region-subfunnels.md).
- **`supervisor`, передающий лиды чужому сотруднику своего региона** — по
  матрице [12 §5](./12-regional-supervisor-rbac.md) технически разрешено
  (`assign`/`transfer` «в пределах своих регионов»), фронтовая модалка это
  не проверяет отдельно — полагается на то, что бэк вернёт `403` на лиды
  вне региона супервайзера, и это корректно попадёт в `result.fail`.

## 7. Массовый перевод на стадию и массовый перенос в воронку (добавлено 12.09.2026)

Продолжение задачи из §1: после «передать сотруднику» попросили ещё два
массовых действия над тем же выбором карточек — **сменить стадию** (без
смены воронки) и **перенести в другую воронку** (без смены владельца).
Оба, как и §1–§6, работают через уже существующие одиночные эндпоинты, вызванные
в цикле — новых ручек бэку заводить не нужно, только верифицировать
поведение под массовым вызовом.

### 7.1. Массовый перевод на стадию

**Фронт:** `Funnel/BulkMoveStageModal.jsx`. Кнопка «На стадию» в панели
массовых действий — активна только если у текущей открытой воронки есть хотя
бы одна стадия.

Эндпоинт — тот же, что у drag&drop одной карточки между колонками:

```
POST /consalting/leads/{id}/move-stage/
{ "stage": "<uuid стадии>" }
```

Список стадий на фронте берётся из уже загруженной доски активной воронки
(`board.columns[].stage`) — отдельный запрос не нужен.

**Что проверить на бэке:**

1. `move-stage` уважает `allowed-transitions` (если `FUNNEL_V2` включён) —
   переход в стадию, недоступную из текущей по правилам воронки, должен
   упасть `400`/`403` с понятным `detail`, а не молча выполниться — фронт
   покажет такие лиды в `result.fail`.
2. Целевая стадия обязана принадлежать **той же воронке**, что и лид —
   `stage` с чужой воронки → `400`.
3. Параллельные `move-stage` по разным `id` (до 4 одновременно, как в §4.3)
   не создают гонок при пересчёте `Funnel.leads_count`/счётчиков колонок.
4. Лид, которого нет в доступе вызывающего (например, чужой регион у
   `supervisor`) → `403`.

Модель прав — та же, что у одиночного drag&drop (уже реализовано и
проверено на проде), отдельной матрицы не требуется.

### 7.2. Массовый перенос в другую воронку

**Фронт:** `Funnel/BulkMoveFunnelModal.jsx`. Кнопка «В другую воронку» в
панели массовых действий — всегда активна (если выбран хотя бы один лид).

В отличие от «Передать сотруднику» (§1–§4, `BulkAssignLeadsModal`), это
**не** меняет владельца — только физическое расположение карточки. Тот же
эндпоинт, что и одиночный перенос кнопкой «В другую воронку»
(`LeadTransferModal`):

```
POST /consalting/leads/{id}/transfer/
{ "target_funnel": "<uuid>", "target_stage": "<uuid>|null" }
```

`owner` в теле не передаётся — по контракту `backend-main-funnel-inbound.md §5`
он должен сохраняться, если явно не задан.

Модалка сначала подгружает список стадий выбранной целевой воронки
(`GET /consalting/funnel-stages/?funnel={id}`, уже существующий эндпоинт) —
чтобы дать выбрать стадию, а не всегда падать в первую; `target_stage: null`
(поле «Первая стадия воронки (по умолчанию)») — бэк подставляет её сам, как
описано в [21-funnel-delete.md](./21-funnel-delete.md) и в §4.2 этого файла.

**Что проверить на бэке:**

1. `transfer` без поля `owner` в теле действительно **не трогает**
   `Lead.owner` — только §1–§4 этого документа полагаются на явную передачу
   `owner`; здесь его нет намеренно.
2. `target_funnel`, равный текущей воронке лида — либо `400` (бессмысленная
   операция), либо no-op без ошибки; фронт такую комбинацию не предлагает
   (список целевых воронок уже исключает текущую), но защититься на бэке
   всё равно стоит на случай прямого вызова API.
3. Перенос в воронку, к которой у вызывающего нет доступа (не входит в
   `filterFunnelsForUser` — например, чужой регион) → `403`. Фронт не
   отправит такую воронку в списке (использует `visibleFunnels`), но это
   не заменяет серверную проверку.
4. `Funnel.leads_count` (см. [20](./20-funnel-leads-count-stale.md))
   пересчитывается консистентно и для исходной, и для целевой воронки после
   каждого переноса — фронт обновляет обе доски по ответу.

### 7.3. Общее для §7.1 и §7.2

- Обе модалки используют общий раннер `bulkLeadOps.js` →
  `runWithConcurrency(items, 4, worker)` — идентичный тому, что уже описан в
  §3.3/§4 для передачи сотруднику (вынесен в отдельный модуль, чтобы не
  дублировать в трёх файлах).
- UX частичного сбоя — тот же паттерн: `N перенесено, M с ошибкой`,
  модалка не закрывается сама, доски обновляются под уже успешные лиды.
- Не в этой итерации (как и в §6): retry только по проваленным лидам,
  фильтрация списка стадий/воронок по региону выбранных лидов.
