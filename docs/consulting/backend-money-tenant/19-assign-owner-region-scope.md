# 19. Назначение владельца лида (`assign_owner_within_region`) должно фильтровать по `consulting_region_codes`

**Приоритет:** P0 — реальный баг на проде, ломает изоляцию регионов для
**входящих WhatsApp-лидов** (через Wazzup), не только для лидов по телефонному
префиксу.
**Дата:** 11.09.2026
**Бэкенд:** `apps/consalting/services/regional_routing.py` (`assign_owner`
/ `assign_owner_within_region`).
**Фронт (не меняется, только диагностика):** `leads/LeadsDistribution.jsx`
(превью «Менеджеры региона» теперь подсвечивает пересечение — см. §4).
**Связано:** [06-regional-funnels-routing.md](./06-regional-funnels-routing.md),
[12-regional-supervisor-rbac.md §3–§4](./12-regional-supervisor-rbac.md),
[15-regional-routing-integration.md](./15-regional-routing-integration.md).

---

## 1. Проблема

Компания подключила WhatsApp (Wazzup) как канал для консалтинга. Входящие
сообщения резолвятся в регион (`wazzup_account_id` → `region_code`, см.
[06 §6.3](./06-regional-funnels-routing.md)), лид создаётся в региональной
воронке — это работает верно. Но **назначение ответственного сейлза**
(`assign_owner_within_region`, [12 §3 шаг 6](./12-regional-supervisor-rbac.md))
берёт кандидатов **только по `assign_role_ids`** (id кастомной роли на
`RegionalFunnelRule`), никак не проверяя `consulting_region_codes` самого
сотрудника.

Если кастомная роль-получатель (например, «Продавец») общая на несколько
региональных правил — а именно так чаще всего и настраивают, потому что в
компании исторически одна роль «Продавец» на всех, — **один и тот же
сотрудник round-robin’ится в оба региона**, независимо от того, к какому
региону он реально привязан.

---

## 2. Причина

`RegionalFunnelRule.assign_role_ids` — это список id **кастомных ролей**
(`custom_role`), не список сотрудников и не фильтр по региону. Пул кандидатов
для round-robin/least-loaded сейчас строится примерно так:

```python
def assign_owner_within_region(lead, rule):
    candidates = User.objects.filter(
        company=lead.company,
        custom_role_id__in=rule.assign_role_ids,
    )
    return pick_by_strategy(candidates, rule.assign_strategy)
```

Если у сотрудника `custom_role` — общая роль «Продавец», и эта роль стоит в
`assign_role_ids` у правил **обоих** регионов (типичная настройка, когда в
компании нет отдельных ролей на регион), он оказывается в пуле `candidates`
для любого региона — вне зависимости от `user.consulting_region_codes`.

Это расходится с моделью данных из [12 §2.2](./12-regional-supervisor-rbac.md):
`salesperson`, заведённый руководителем региона, получает
`consulting_region_codes = [<регион руководителя>]` — то есть у сотрудника
**уже есть** авторитетное поле «в каком регионе он работает», но
`assign_owner_within_region` его не использует.

## 3. Фикс

Пересечь кандидатов с регионом лида **дополнительно** к роли — регион
становится обязательным фильтром, роль — уточняющим (как и раньше, чтобы
разработчик мог держать в одном регионе несколько ролей: «Продавец»,
«Старший продавец» и т.д.):

```python
def assign_owner_within_region(lead, rule):
    region = rule.region_code
    candidates = User.objects.filter(
        company=lead.company,
        custom_role_id__in=rule.assign_role_ids,
        consulting_region_codes__contains=[region],   # НОВОЕ — обязательный фильтр
    )
    if not candidates.exists():
        # осознанный fallback, не тихий: лид остаётся owner=None,
        # чтобы руководитель региона распределил вручную, а не улетел
        # в другой регион по роли.
        audit_log(
            "regional.assign_owner.empty_pool",
            region=region, rule_id=rule.id,
        )
        return None
    return pick_by_strategy(candidates, rule.assign_strategy)
```

**Важно:**

- `owner/admin/rop` не имеют `consulting_region_codes` (пусто = «все регионы»
  по [12 §2.2](./12-regional-supervisor-rbac.md)) — их **не следует** включать
  в пул автоназначения по умолчанию (это операционные роли, не сейлзы), но
  если политика компании это допускает — фильтровать явным флагом, не через
  пустой список кодов.
- Если после фильтра пул пуст (роль указана, но ни один сотрудник этой роли
  не привязан к региону) — **не** откатываться на «весь пул по роли без
  региона». Молчаливый откат воспроизведёт именно этот баг. Лид должен
  остаться `owner=None` в своей региональной воронке — руководитель региона
  назначит вручную (или добавит сотрудника в регион).
- Не трогать `assign_role_ids` как механизм — компаниям с уже разведёнными
  ролями на регион («Продавец Бишкек» / «Продавец Ош») фикс ничего не
  меняет, пул и так был правильным по совпадению.

## 4. Что уже сделано на фронте (диагностика, не блокер)

Чтобы админ видел проблему конфигурации ещё до прихода реальных лидов,
`leads/LeadsDistribution.jsx` теперь считает пересечения сотрудников между
региональными правилами (`crossRegionEmployeeIds`) и показывает
предупреждение прямо в карточке региона:

> ⚠ Пересечение с другим регионом: <имя> — эти сотрудники состоят в роли,
> выбранной сразу в нескольких региональных правилах, и будут получать лиды
> из чужого региона по round-robin.

Это **не исправляет** серверную логику — только подсвечивает конфигурацию,
которая приведёт к багу при текущем бэкенде. После фикса из §3 предупреждение
всё ещё полезно (тот же сотрудник в двух правилах — двусмысленная настройка),
но перестаёт означать гарантированную утечку между регионами, раз сервер
дополнительно фильтрует по `consulting_region_codes`.

## 5. Чек-лист приёмки

- [ ] Два региональных правила с **одинаковым** `assign_role_ids`, но
      сотрудники в каждом регионе разные (`consulting_region_codes=["bishkek"]`
      vs `["osh"]`) → round-robin никогда не назначает лид Оша сотруднику
      Бишкека и наоборот.
- [ ] Воспроизвести кейс из §1 (3 WhatsApp-сообщения подряд, 2 Бишкек + 1 Ош)
      → все Бишкек-лиды достаются только сотрудникам с `"bishkek"` в
      `consulting_region_codes`.
- [ ] Пул кандидатов пуст (роль указана, но нет сотрудников региона) → лид
      создаётся с `owner=null` в региональной воронке, **не** уходит
      сотруднику другого региона; событие в audit log.
- [ ] Компании с уже разведёнными ролями на регион — поведение не изменилось.
- [ ] `least_loaded` и `round_robin` обе стратегии учитывают фильтр по
      региону (не только `round_robin`, который был в примере теста).
- [ ] Повторное WhatsApp-сообщение в тот же чат не меняет уже назначенного
      владельца ([12 §3](./12-regional-supervisor-rbac.md) — регион/воронка
      лида не пересчитываются повторно, значит и владелец не переназначается).
