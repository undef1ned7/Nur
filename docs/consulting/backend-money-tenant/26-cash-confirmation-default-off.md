# 26. Подтверждение кассы: дефолт меняется на «выключено»

**Приоритет:** P1 — меняет денежное поведение по умолчанию для всех компаний
без явно сохранённых настроек кассы.
**Дата:** 16.09.2026
**Бэкенд:** изменить дефолт поля `CashConfirmationSettings.mode` с `cash_only`
на `off`; решить, что делать с уже существующими строками (см. §3).
**Фронт (реализовано):** `src/utils/consultingMoney.js`
(`DEFAULT_CASH_CONFIRM_MODE = "off"`, `normalizeCashConfirmMode` без данных
теперь возвращает `off`), `Kassa/KassaSettings.jsx` (дефолт формы `off`,
текст заглушки), `Kassa/Kassa.jsx` (вкладка «Запросы» скрыта, пока
`mode="off"` и нет ни одной заявки `pending`).
**Связано:** [00-money-flow.md](./00-money-flow.md) §5,
[03-cash-confirmation.md](./03-cash-confirmation.md),
[09-frontend-contract.md](./09-frontend-contract.md) §9.0 п.1b, §9.3.

## 1. Формулировка задачи

Запрос от продукта: «в кассе есть запросы [на подтверждение поступления],
нужно сделать так, чтобы эти запросы можно было выключить, по умолчанию
должно быть выключено».

Разобрал на два требования:

1. **Возможность выключить** — уже реализована: `CashConfirmationSettings.mode`
   поддерживает значение `off` (раздел «Касса → Настройки»,
   [03-cash-confirmation.md](./03-cash-confirmation.md) §9.2). Ничего нового
   создавать не нужно — переключатель уже есть.
2. **По умолчанию выключено** — вот это раньше не выполнялось: и в спеке
   ([03-cash-confirmation.md](./03-cash-confirmation.md)), и на фронте
   (`KassaSettings.jsx`, `consultingMoney.js`) дефолтным режимом был
   `cash_only` («заявка только для наличных»). То есть компания, ни разу не
   открывавшая настройки кассы, **уже получала** заявки на подтверждение по
   каждой наличной продаже — незаметно для себя.

Это и есть суть задачи: не «добавить кнопку выключения», а **сменить
дефолт**, чтобы деньги по умолчанию сразу шли в остаток кассы без
дополнительного шага подтверждения, а компания сама включала подтверждение,
если оно ей нужно (розница с несколькими кассирами, риск расхождений и т.д.).

## 2. Что меняется на бэке

`docs/consulting/backend-money-tenant/03-cash-confirmation.md`, модель
`CashConfirmationSettings`:

```python
class CashConfirmationSettings(models.Model):
    class Mode(models.TextChoices):
        OFF = "off", "Выключено"
        CASH_ONLY = "cash_only", "Только для наличных"
        ALWAYS = "always", "Всегда"

    company = models.OneToOneField(Company, on_delete=models.CASCADE,
                                   related_name="cash_confirmation")
    mode = models.CharField(max_length=16, choices=Mode.choices,
                             default=Mode.OFF)          # было Mode.CASH_ONLY
    skip_for_cashier = models.BooleanField(default=True)
    overdue_hours = models.PositiveIntegerField(default=24)
```

`GET /consalting/cashbox/confirmation-settings/` для компании без сохранённой
строки должен создавать её (или отдавать виртуальный дефолт) со значением
`mode="off"`, а не `cash_only`.

Логика `needs_confirmation` (см. [03](./03-cash-confirmation.md) §9.3) не
меняется — при `mode="off"` она и раньше возвращала `False`. Меняется только
то, какое значение `mode` компания получает, ничего не настраивая руками.

## 3. Что делать с уже существующими строками (решение продукта)

Это ключевая развилка, и её нельзя закрыть молча миграцией «на всякий случай»:

| Вариант | Поведение | Когда уместен |
|---|---|---|
| **A. Не трогать существующие строки** (рекомендация) | Компании, которые уже явно сохранили `mode` (в том числе неявно — через дефолт `cash_only`, если строка была создана `get_or_create`), остаются как есть. Новый дефолт `off` применяется только к компаниям, у которых строки `CashConfirmationSettings` ещё нет на момент релиза | Безопасно: ни одна компания, уже полагающаяся на заявки в кассу, не потеряет их без предупреждения |
| B. Принудительно сбросить в `off` все строки с `mode="cash_only"` | Считаем, что раз это дефолт, никто его осознанно не выбирал | Рискованно: часть компаний могла явно выбрать `cash_only` в настройках, потому что он им нужен — такую компанию нельзя отличить от «просто не трогали дефолт» без доп. поля |

**Выбираем вариант A.** Чтобы вариант B стал возможен в будущем (если продукт
решит, что нужно), заранее добавить на бэке поле-маркер, а не молчаливую
эвристику:

```python
    mode_set_explicitly = models.BooleanField(default=False)
```

— проставлять `True` при любом `PUT/POST confirmation-settings/` с телом от
пользователя. Тогда можно будет безопасно сегментировать «дефолт vs выбор
пользователя» задним числом. Для текущей задачи это поле не обязательно
использовать в логике `needs_confirmation`, только для будущей аналитики/
миграций — если это усложняет спринт, можно отложить и просто не трогать
существующие строки (вариант A без маркера тоже допустим).

### Data-миграция

- Новый дефолт поля (`default=Mode.OFF`) применяется автоматически ко всем
  **новым** строкам `CashConfirmationSettings`, создаваемым после релиза
  (новые компании, либо старые компании при первом ленивом создании строки).
- Django-миграция **не должна** трогать уже существующие строки таблицы
  (`RunPython` с изменением данных не нужен) — только `AlterField` на
  `default`.

## 4. Фронт (уже сделано)

- `src/utils/consultingMoney.js`: добавлена константа
  `DEFAULT_CASH_CONFIRM_MODE = "off"`; `normalizeCashConfirmMode(undefined)` и
  любое нераспознанное значение теперь нормализуются в `off` (было
  `cash_only`); `CASH_CONFIRM_MODE_OPTIONS` переупорядочен — `off` первым, с
  пометкой «(по умолчанию)».
- `Kassa/KassaSettings.jsx`: `DEFAULTS.mode` — `off`; текст заглушки
  «эндпоинт ещё не подключён» теперь говорит про выключенное подтверждение
  вместо «только для наличных».
- `Kassa/Kassa.jsx`: подгружает `confirmation-settings` при открытии раздела
  «Касса»; вкладка **«Запросы»** скрывается из навигации, если `mode="off"`
  **и** нет ни одной заявки со статусом `pending` (если старые заявки
  остались — например, режим только что переключили — вкладка не
  прячется, чтобы их не потерять из вида). Если пользователь оставался
  на скрытой вкладке — рендерится «Касса» вместо неё.

Никаких изменений в оплатах, отменах, аналитике не требуется: они уже
ветвятся по значению `mode`, а не по его конкретному дефолту.

## 5. Чек-лист приёмки

- [ ] Новая компания (нет строки `CashConfirmationSettings`) →
      `GET /consalting/cashbox/confirmation-settings/` возвращает
      `{"mode": "off", ...}`.
- [ ] Продажа наличными в новой компании сразу создаёт `CashOperation`
      (не `CashRequest`), `Sale.status = completed` сразу.
- [ ] Существующие компании, у которых `mode` уже сохранён в БД (в т.ч. как
      `cash_only`), **не меняются** этим релизом.
- [ ] `POST confirmation-settings/ {"mode": "cash_only"}` по-прежнему
      переключает поведение как раньше — регресса в логике режимов нет.
- [ ] `GET .../confirmation-settings/` продолжает отдавать `mode` в каноне
      `required | cash_only | off` (легаси-алиасы `always`/`auto` на входе,
      не в ответах — см. [09-frontend-contract.md](./09-frontend-contract.md) §9.0 п.1).
